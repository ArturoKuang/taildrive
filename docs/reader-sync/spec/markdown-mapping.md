## 1. Per-book file layout

Reader has two on-disk layouts today.

### Sidecar package (no vault, or vault writing off)

A `.reader` directory next to the book (`<stem>.reader/`), or if that folder isn't writable, `Application Support/Sidecars/<bare-sha256-hex>.reader/` (`Sidecar.swift:204–205, 307–319`). Files written together (`Sidecar.swift:81–116`):

| File | Role today | Sync v1 |
|---|---|---|
| `notes.md` | `NotesDocument` — full `NoteEntry` fields | Synced as note records |
| `highlights.md` | `HighlightsDocument` — full `HighlightEntry` fields | Synced as highlight records |
| `words.md` | `WordsDocument` — `WordEntry` + nested `LookupEntry` | Synced as word records **plus separate lookup records** (`l_…`, `wordId`). Nesting is a markdown detail only |
| `marks.md` | Local vim-style marks for this book | **Mac-local, not synced.** No record type. Vault flush does not write marks (`App/Reader/VaultCoordinator.swift:189–197`). Global marks live in Application Support `global-marks.md` (`Marks.swift:280–298`). |
| `state.json` | `ViewState` (page, zoom, bookmarks, rotations, window, EPUB theme) | **Mac-local, apart from the reading position**, which is projected to and from the `position` record (§2). Everything else is local. Bookmarks live here (`Models.swift:93`), not as records. Vault books store the same `ViewState` inside `.reader-state.json` (`Vault.swift:105–145`). |

Decided (Q2, rev 3): v1 does not sync marks, bookmarks, panes, reading settings or Ask AI history. Only the reading position leaves `ViewState`, as the `position` record.

### Vault book folder (what Reader writes into Obsidian)

When the book is in a vault and writing is on, Reader does not use the sidecar files. It writes into the book folder (`App/Reader/VaultCoordinator.swift:189–197, 248–297`; `Vault.swift:148–160`):

| Path | Role | Sync v1 |
|---|---|---|
| `notes/` (default; `notesFolder` is configurable) | One `.md` per chapter (`Chapter N.md`) or `{Book Title}.md`. Each highlight or note is an owned block with a `reader://open` link. | Projection of highlight + note records. **Lossy** vs the sidecar (see §2). |
| `learner/vocabulary.md` if present, else `words.md` (or a configured relative path) | Vocabulary entries. Only ids starting `w_` are written back. | Projection of word records. **Lossy.** |
| `.reader-state.json` | `VaultBookSettings`: enabled flag, folder paths, `view`, and a `marksMarkdown` field | Mac-local. `marksMarkdown` is persisted if set, but no current writer was found in `VaultCoordinator`. |

User text outside `<!-- reader:begin id=… -->` / `<!-- reader:end -->` is copied through unchanged (`OwnedBlocks.swift:3–4, 74`). Curriculum, tutor, and mastery files exist in some book folders and are out of scope for sync v1 (assumption: not records).

The live vault already uses `books/<slug>/` with the book file at the folder root, plus `notes/` and sometimes `learner/`, `curriculum/`, `book/`, `CLAUDE.md`. **Copying a book into `books/` on first highlight is not in the current code** — it is planned.

## 2. Record types and field mapping

IDs are client-made. New highlight, note, lookup, and mark ids use `IDs.make(prefix)` → `prefix + "_" + lowercase UUID without hyphens` (`Paths.swift:64–67`). Prefixes used by the app: `h`, `n`, `l`, `m`, and `b` (bookmarks, local only). Word ids are **not** UUIDs: `"w_" + WordStore.normalize(word)` (trim + lowercase) (`App/Reader/ReaderSession.swift:481`).

Sidecar records are stored as `<!-- reader {compact JSON} -->` (`JSONValue.swift:250–262`). Object keys are sorted. `--` in strings is escaped as `\u002d\u002d` so the comment cannot close early (`JSONValue.swift:89–96`). Unknown JSON keys become `extras` and are written back (`MarkdownDocuments.swift:90–92, 201, 327, 469, 524`). Suggested wire names follow the Swift properties; where the comment key differs, it is noted.

### FrontMatter (sidecar file header, not a row)

YAML between `---` lines (`MarkdownDocuments.swift:11–51`). The key `reader:` is the kind (`notes` / `highlights` / `words` / `marks`). **FrontMatter is not a wire record (D4).** The server writes book records. Reader registers a file with `POST /v1/books {sha256 (bare hex), size, format, docId, title, filename}` and re-keys local records to the returned `bookId`.

| document | `String` | `document:` | `document: string` | Filename, e.g. `Book.pdf` |
| fingerprint | `String` | `fingerprint:` | `fingerprint: string` | `sha256:` + hex. See §4 |

## 3. Block ids, `applyExternal`, and the server as source

### Sidecar files have no block markers

`notes.md` / `highlights.md` / `words.md` identify records by the `id` (or `lookup`) key inside `<!-- reader … -->`. The whole file is rewritten from records on save (`Sidecar.swift:107–115`; `App/Reader/ReaderSession.swift:182–189`). Hand text outside those comments is not preserved.

### Vault notes: owned-block ids

```
<!-- reader:begin id=h_… -->
…body…
<!-- reader:end -->
```

Rendered by `OwnedBlocks.render` (`OwnedBlocks.swift:28–29`). Parse (`OwnedBlocks.swift:32–68`):

- Begin token is the literal `<!-- reader:begin id=`; the id runs to the next ` -->`; surrounding whitespace on the id is trimmed.
- One leading and one trailing newline are stripped from the body.
- Text outside the markers is a user slice, kept byte-for-byte on upsert (`OwnedBlocks.swift:74–86`).
- A begin without a matching end, or without ` -->`, is treated as user text, not an owned block.
- `upsert` replaces the first block with that id, or appends (inserting a blank line if the file does not already end in `\n`).
- `remove` drops the block and concatenates the remaining raw slices.

Vault block bodies also end with an Obsidian block id `^id` (`VaultNotes.swift:65`) so `obsidian://open?vault=…&file=…#^id` works (`ReaderLink.swift:82–89`). The Reader-owned id is the HTML comment, not the `^` line. Parse skips `^` lines (`VaultNotes.swift:130`).

### `VaultSync.applyExternal` today

`VaultSync.swift:16–37`, called from `VaultCoordinator.mergeExternal` (`App/Reader/VaultCoordinator.swift:225–245`). For each pending id, compare the Reader body and the disk body against the last-written baseline:

- Both changed and the bodies differ → conflict: concatenate the Reader body + `\n\n> [!warning] Also changed outside Reader\n>\n> ` + the remote body (newlines prefixed with `> `), upsert that into the **same** file, and return the id in `conflicts`. The toast is "Kept both versions of a note". User text before the block is kept (`Tests/ReaderCoreTests/VaultTests.swift:175–189`).
- Only Reader changed → upsert the pending body.
- Only disk changed (or Reader still matches the baseline) → leave the disk body.

`isOwnWrite` is a byte-equal check against `lastWritten`, so the folder watcher ignores Reader's own flush (`VaultSync.swift:40–43`).

### What changes when the server is the source

Assumption, mapping the locked rule onto this code:

- Records on the server are the source. Each record carries its client id and a **base version**. Reader writes vault markdown from the accepted records; the markdown file is not the store.
- **Q7: what Reader pushes.** Reader pushes the session model. In vault mode, the session is rebuilt from the parsed vault files on open and on every external change (`App/Reader/VaultCoordinator.swift:53, 111–113, 117–177`), so hand edits flow through it. Fields the vault can't carry (prefix, suffix, rects, extras, timestamps, scope, ai, provider, the distinct noteID) are filled from the local sync store's last accepted record, never blanked. A field is pushed only when the parsed value differs from the last projection.
- A change from only one side wins (same as today when only Reader or only disk changed).
- When both sides change the same record, the server keeps **both versions** and Reader asks which one to keep. **Do not** write the `Also changed outside Reader` callout, or any conflict file, into the vault.
- Sync `version` is not `FrontMatter.version`. The markdown `version:` key is the file format (currently 1).
- Hand edits in Obsidian become record updates as follows: on file change, parse owned blocks; for each id, if the parsed fields the file actually carries (quote, note prose, color, `reader://` `loc`) differ from the last projection of the accepted record, push an update with that record's base version. User slices outside markers are not records and are not uploaded. A block Reader previously wrote that is now gone from a file that still exists is a delete, pushed as a tombstone. A missing or renamed file is never a delete (§3.3). A new hand-written owned block, or a vocab entry with a new id, is a create.
- Vault markdown cannot represent prefix, suffix, rects, extras, timestamps, or a distinct note id. Those fields stay on the record. Assumption: adopting a hand-edited quote does not blank prefix/suffix/rects; Reader should reanchor after adopting the new quote.


### 3.3 Delete rule (D6 / Q-M1)

**Today** (from reading the code, not run): `reload` rebuilds highlights only from the notes files that exist (`App/Reader/VaultCoordinator.swift:127–161`). If a whole file is deleted while the book is open, its highlights drop out of the session. Its notes are re-added only because of the `mergePending` path (`:162–169`), so a highlight-with-note becomes a plain note and loses its color. If Reader was closed, everything in that file is just gone at the next open. A rename inside the notes folder is still parsed (`:127–128`), but the section comes from the new filename (`:134`; `Vault.swift:68–82`). The next flush moves those blocks back into `Chapter N.md` or `{Title}.md` and removes them from the renamed file (`:258–273`).

**v2 rule:**
1. Tombstones come from exactly two sources: an explicit delete in Reader's UI (or the phone), or a block id that was in Reader's last projection of a file that **still exists and parsed**, and is no longer in that file **or in any other notes file for the book**. A block found in another file has moved, which is not a delete.
2. A notes file that is missing, renamed, moved out of the notes folder, or unreadable pushes **nothing**. Those records stay live on the server and in the session (from the local sync store). Reader shows "Chapter 3.md is missing · 12 highlights kept" with **Restore file** (re-project) or **Delete them** (explicit tombstones).
3. If the notes folder or vault can't be listed, or comes back empty while records exist, the vault is treated as unavailable and nothing is pushed.
4. Guard: if one reload would tombstone more than 5 records, or more than 50% of a book's records, Reader asks first.
5. Phone/server deletes remove the owned block. User text outside the markers is never touched.

### 3.4 Migrating `Also changed outside Reader` callouts (D7 / Q-M2)

Written by `VaultSync.applyExternal` (`VaultSync.swift:27–30`) through `VaultCoordinator.mergeExternal` (`App/Reader/VaultCoordinator.swift:240–244`, toast "Kept both versions of a note"). The callout is written **inside** the owned block, after `^id`, with the whole other block quoted one level deeper. Verified by running real ReaderCore: on reload, `VaultNoteFile.parseBody` folds the callout line and the whole quoted remote block, including its link and `^id`, **into the highlight's `quote`** (`VaultNotes.swift:117–122`). The body stays the Reader side. Pushing as-is would sync a corrupted quote.

One-time migration, per book, before its first push:
1. Stop writing callouts: remove the conflict branch at `VaultSync.swift:27–30` and the toast at `VaultCoordinator.swift:241–243`. Reader's server conflict UI replaces them.
2. Scan the book's notes files for owned blocks whose body contains a line equal to `> [!warning] Also changed outside Reader`. Callouts outside markers are user text and are left alone.
3. Split the body at that line. Side A is the text before it. Side B is the lines after it with one `> ` level stripped, which gives a full block. Parse each with `parseBody`. A second callout nested inside side B is kept as literal text and flagged.
4. Push A with `baseVersion 0` (it becomes v1). Then push B with `baseVersion 0`: per rev 3 §6 (`b < h`, not same), that opens a server conflict with sides [A, B] and `base: null`. Identical sides are a noop, and nothing more is needed.
5. Don't rewrite the block. The vault text stays exactly as it is until the user resolves the conflict in Reader. Then Reader re-renders the block from the resolved record, which drops the callout. User text outside the markers is untouched.
6. Dry run first. List the books, files and block ids, and copy each affected file to `Application Support/Reader/Sync/migration/<bookId>/` (outside the vault) before any later rewrite.

## 4. Book identity

**Fingerprint** (`SHA256.swift:80–82`; `Sidecar.swift:198`; `App/Reader/ReaderSession.swift:115`):

```
SHA256.fingerprint(bookData) == "sha256:" + lowercase hex(SHA-256 of the entire file bytes)
```

Pure-Swift FIPS 180-4 SHA-256 of the whole `Data` (PDF or EPUB). Known vectors in `Tests/ReaderCoreTests/CoreTests.swift:6–9`: empty → `sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`; `"abc"` → `sha256:ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`.

The Application Support sidecar folder uses the **bare** hex, with no `sha256:` prefix (`Sidecar.swift:281, 316`).

**pdfID** (`Sidecar.swift:170–185, 201`): last `/ID` in the file decoded as ISO-Latin-1; first `<…>` after it; keep hex digits only; lowercase. The second ID in a pair is ignored (`CoreTests.swift:12–14`: `/ID [<4B1E77C0><99AA>]` → `4b1e77c0`). The comment says "PDFKit on the Mac is the fallback" (`Sidecar.swift:171–173`); **no PDFKit fallback is implemented** — `SidecarStore.open` only calls `PDFIdentity.scan`.

**epubID** (`Sidecar.swift:202`; `EPUB.swift:103, 129`): first `dc:identifier` in the OPF metadata, trimmed. Empty string if missing.

**Match rule** (`Sidecar.swift:334–337`): equal fingerprints → `.exact`; else a non-empty matching pdfID or epubID → `.stableID` (the sidecar fingerprint is rewritten); else `.different` (reanchor by quote + prefix + suffix, `Reanchor.swift:38–46`).

**Mismatch with the server's SHA-256 of file bytes:**

1. Reader's stored fingerprint includes the `sha256:` prefix; the server should accept or strip it. Bare hex is already used for the Application Support directory name.
2. A small edit to a book changes the SHA-256 but not pdfID/epubID. Reader treats that as the same book (`.stableID`) and refreshes the fingerprint. A server that addresses books only by SHA-256 of bytes would treat it as a new book and miss the annotations.
3. Opening a vault book records the fingerprint only — `pdfID` and `epubID` are stored as nil (`Sidecar.swift:349`; `App/Reader/ReaderDocument.swift:30–47`). Those books will not get `.stableID` matching until that path is filled in.

**v2 (D10):** fill `pdfID`/`epubID` on the vault open path, at `ReaderDocument.swift:30` (`FrontMatter` identity) and `SidecarStore.noteVaultBook` (`Sidecar.swift:342–350`, which passes nil today), using the same calls as `SidecarStore.open` (`Sidecar.swift:201–202`). Send them as `docId` at register.
- **PDF:** `PDFIdentity.scan` (`Sidecar.swift:174–185`) first, then `CGPDFDocument(url).fileIdentifier[0]` as hex for trailers the scan can't read. Verified on the mini: both gave the same value on a generated PDF. PDFKit `documentAttributes` has no ID (keys seen: CreationDate, ModDate, Producer).
- **EPUB:** Reader takes the **first** `dc:identifier` (`EPUB.swift:103, 129`), not the one named by `<package unique-identifier=…>`. Better: prefer the `unique-identifier` target and fall back to the first `dc:identifier`. This changes `epubID` only for EPUBs whose first identifier isn't the unique one.

## 5. `reader://` link format

Exactly as `ReaderLink.swift:14–44, 21–22, 46–54` and `Query` at `ReaderLink.swift:93–102`.

```
reader://open?path=<escaped>&loc=<escaped>&id=<escaped>
```

- Parse requires the prefix `reader://open?` and a non-empty `path`. A `#` fragment, if present, is discarded.
- Query items, in this write order: `path` (required), `loc` (omitted if nil/empty), `id` (omitted if nil/empty). Joined with `&`.
- Escape: percent-encode everything except `A–Z a–z 0–9 -._~`. Unescape is `removingPercentEncoding`.
- `path` is the filesystem path of the book file (absolute on the Mac that wrote it).
- `loc` for a PDF is `page=N` or `page=N&y=120` (`pageNumber` splits on `&` or `;` and reads `page=`). For an EPUB it is the raw CFI (`epubcfi(…)`); `pageNumber` returns nil when `loc` starts with `epubcfi(`.
- `id` is the highlight or note id.
- Markdown: `[↗ Open in Reader](reader://open?…)`.
- **v2 (D8):** new links append `fp=<bookId>` (`sha256:<hex>`, escaped). Resolve by `fp`, meaning the `bookId` or any of the book's `files[].sha256`, then fall back to `path`. `path` stays required for older Readers (`ReaderLink.swift:42`).

`PassageIdentity.cfi` treats a location starting with `page=` as not a CFI (`Annotations.swift:77–81`). Vault write prefers CFI, else `page=N` (`App/Reader/VaultCoordinator.swift:309–312`).

## 6. Open questions and risks

- Hand-written text inside sidecar `notes.md` / `highlights.md` / `words.md` is lost on the next render; only vault owned-block files preserve user slices. Which files are "managed" once books live in `books/`?
- Vault projection is lossy: prefix, suffix, rects, extras, timestamps, scope, and a distinct `noteID` do not survive a vault reload. Records must stay canonical; adopting a hand edit must not blank those fields.
- *(Resolved v2, §3.3)* Deletes have no tombstone in markdown. Vault removes a block only if its id was in `loadedBlockIDs` (`App/Reader/VaultCoordinator.swift:266–268`). A delete from the phone should remove the block; a user deleting the block in Obsidian should delete (or tombstone) the record. Ambiguous if the whole file is gone.
- Ordering: sidecar render sorts notes/highlights by page then id, words by first-lookup page then word, marks by symbol. Vault upsert keeps an existing block's position and appends new ones. Sync should not treat reorder-only diffs as edits.
- *(Resolved v2, D1)* Both. The word is a record with a deterministic id, and each lookup is its own `l_` record. Equal word creates are a noop on the server.
- *(Resolved v2, D5)* Two records linked by `highlight.noteId`. Vault notes keep reusing the highlight id.
- *(Resolved v2, §3.4)* Callouts stop, and existing ones migrate into server conflicts.
- *(Resolved v2, D12)* Hand-written vocabulary (ids `hand-…`) is not synced in v1 (`App/Reader/VaultCoordinator.swift:281`).
- Copying a book into `books/` on first highlight is not in the current code. Folder slug vs title vs fingerprint is unspecified.
- *(Resolved v2, D8)* `reader://` gains `fp=<bookId>`.
- *(Resolved v2, D9, verified)* Rects come from `selection.bounds(for: page)` (`App/Reader/PDFContainerViewController.swift:398–403`). Rotation is applied through `PDFPage.rotation` (`App/Reader/ReaderSession.swift:446–451`). A probe on the mini showed identical bounds at rotation 0 and 90, so rects are unrotated page space.
- `FrontMatter.version` vs record base version: easy to confuse on the wire.
- Curriculum / `CLAUDE.md` / mastery / events are in real book folders and are not records. Confirm they stay out of sync v1.
